1Case background

VP Education

Plans each meeting. Needs to know who takes which role, who has not been on stage for a while, and how far each member is on their Pathways path.

VP Membership

Keeps the club healthy. Needs to know how many members are active and whose dues are overdue.

Area Director

Supports several clubs. Needs to spot clubs with too few members and compare activity across the area.

The problem

  • Scattered records. Role sheets, speech logs and member lists live in separate spreadsheets, so they are hard to cross-check.
  • Inconsistent data. The same person is written in different ways in different files.
  • Slow answers. Questions like “who has never taken a role?” take a lot of manual counting.

The solution

Put members, clubs, meetings, roles and speeches into one normalized relational database, so each of these questions becomes a single SQL query.

Relationships

Cardinality ratio is 1:1, 1:N or M:N. Participation: total (double line, every row must take part, enforced by a NOT NULL foreign key) or partial (single line, may have none). In the diagram, || means exactly one, |o zero or one, o{ zero or more. There is no 1:1 relationship in this design.

Key design decisions

DecisionReason
memberships is its own tableA member can belong to more than one club, so members and clubs are M:N. A relational table cannot store M:N directly, so it is split into two 1:N relationships. The dues date paid_through belongs to one membership, not to the person.
role_assignments key is (meeting_id, role_code)Each role in a meeting can be taken by only one person. The composite primary key lets the database block double bookings.
Speech evaluators are stored in speeches.evaluator_idA meeting has several evaluators. As a role, the composite key would reject the second one. Each evaluator is tied to exactly one speech, so the column belongs on the speech.
status and paid_through are separatestatus says whether the person is still in the club; paid_through says how far dues are paid. “Still in the club but not renewed” is the combination of both.
Time limits stored on each speechDifferent projects have different limits, so min_sec/max_sec are needed to judge each speech.
No phone, email or address columnsNone of the questions need them. Collecting only what is needed protects privacy.
Third normal form (3NF)Every non-key column depends only on its table’s key. For example, a club’s area is stored only in clubs, never repeated in meetings.

About the SQL engine

This page runs SQLite in your browser through sql.js, because GitHub Pages cannot host a database server. All practice SQL is written so it also runs on MySQL 8.0+, and every query and comparison on this page was checked on MySQL 8.4 with identical results. A few behaviours differ:
