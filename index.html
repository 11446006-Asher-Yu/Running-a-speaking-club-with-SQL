1Case background案例背景

VP Education教育副會長

Plans each meeting. Needs to know who takes which role, who has not been on stage for a while, and how far each member is on their Pathways path.

負責規劃每場例會。需要知道誰擔任什麼角色、誰很久沒上台，以及每位會員的 Pathways 進度。

VP Membership會員副會長

Keeps the club healthy. Needs to know how many members are active and whose dues are overdue.

負責維持分會的會員人數。需要知道目前有幾位有效會員、誰的會費還沒續繳。

Area Director區域總監

Supports several clubs. Needs to spot clubs with too few members and compare activity across the area.

負責輔導好幾個分會。需要找出人數偏少的分會，並比較區域內各分會的活動狀況。

The problem要解決的問題

  • Scattered records. Role sheets, speech logs and member lists live in separate spreadsheets, so they are hard to cross-check.
  • Inconsistent data. The same person is written in different ways in different files.
  • Slow answers. Questions like “who has never taken a role?” take a lot of manual counting.
  • 資料分散。角色表、演講紀錄和會員名單分別放在不同的試算表，很難交叉比對。
  • 資料不一致。同一個人在不同檔案裡有不同的寫法。
  • 統計很慢。像「誰從來沒擔任過角色？」這種問題，要花很多時間人工計算。

The solution解決方式

Put members, clubs, meetings, roles and speeches into one relational database where each fact is stored only once, so each of these questions becomes a single SQL query.

把會員、分會、例會、角色和演講放進同一個關聯式資料庫，讓每件事只存一次。這樣上面每個問題都只要一段 SQL 就能回答。

Relationships關係

Cardinality ratio is 1:1, 1:N or M:N. Participation: total (double line, every row must take part, enforced by a NOT NULL foreign key) or partial (single line, may have none). In the diagram, || means exactly one, |o zero or one, o{ zero or more. There is no 1:1 relationship in this design.

基數比分為 1:1、1:N、M:N。參與方式分為全參與（雙線：每一列都一定要參與，由 NOT NULL 的外鍵保證）和部分參與（單線：可以沒有）。圖中 || 表示剛好一個，|o 表示零或一個，o{ 表示零或多個。這份設計沒有 1:1 的關係。

Key design decisions主要設計決策

Decision決策 Reason理由
memberships is its own tablememberships 獨立成一張表 A member can belong to more than one club, so members and clubs are M:N. A relational table cannot store M:N directly, so it is split into two 1:N relationships. The dues date paid_through belongs to one membership, not to the person.一位會員可以同時屬於多個分會，所以會員和分會是 M:N。關聯式資料表無法直接存 M:N，所以拆成兩個 1:N。會費日期 paid_through 屬於「某人在某分會的會籍」，不是屬於這個人。
role_assignments key is (meeting_id, role_code, member_id)role_assignments 的主鍵是（meeting_id, role_code, member_id） At special events one role can have two people (e.g. co-hosts), and in small clubs one person often takes two roles, so neither (meeting_id, role_code) nor (meeting_id, member_id) is a key. The three columns together only block recording the same person in the same role twice. Trade-off: the database no longer stops two timers being booked by mistake; whoever schedules the meeting has to check that.特殊活動時一個角色可能有兩個人（例如雙主持），小分會也常有一人兼任兩個角色，所以（meeting_id, role_code）和（meeting_id, member_id）都不能當鍵。三個欄位一起當主鍵，只擋掉「同一人在同一場例會重複登記同一個角色」。代價是：資料庫不會再擋下誤排兩位計時員的情況，要由排角色的人自己檢查。
club_roles: each club’s own role listclub_roles：每個分會自己的角色清單 Clubs offer different roles (e.g. only some have a photographer) and use different names for the same role (e.g. “Toastmaster of the Day”). roles keeps one standard list; club_roles records which roles a club offers and the name it uses. Trade-off: the database does not check that a meeting only uses roles its club offers, because role_assignments has no club_id, and adding one would store the meeting’s club a second time.各分會的角色不一樣（例如只有部分分會有攝影師），同一個角色的名稱也可能不同（例如「Toastmaster of the Day」）。roles 保留一份標準清單；club_roles 記錄每個分會有哪些角色、在該分會叫什麼名字。代價：資料庫不會檢查例會只使用該分會有的角色，因為 role_assignments 沒有 club_id；如果加上去，就等於把例會所屬的分會再存一次。
Speech evaluators are stored in speeches.evaluator_id個別講評員記在 speeches.evaluator_id Each evaluator evaluates one specific speech. role_assignments only says who took a role in which meeting, not which speech they evaluated, so the evaluator is stored on the speech itself. Speeches are entered while the agenda is being planned, often before the speaker or the evaluator is found, so both member_id (speaker) and evaluator_id allow NULL, meaning “not known yet”. Every speech ends up with one speaker and one evaluator; the sample meetings are all in the past, so none of them is NULL.每位講評員講評的是某一場特定的演講。role_assignments 只記錄「誰在哪場例會擔任什麼角色」，記不了「講評哪一場演講」，所以講評員直接記在演講上。演講資料在排議程時就會建立，那時常常還沒找到講者或講評員，所以 member_id（講者）和 evaluator_id 都允許 NULL，代表「還不知道」。每場演講最後都會有一位講者和一位講評員；樣本資料的例會都已經結束，所以沒有 NULL。
status and paid_through are separatestatus 和 paid_through 分開 status says whether the person is still in the club; paid_through says how far dues are paid. “Still in the club but not renewed” is the combination of both.status 記錄這個人還在不在分會；paid_through 記錄會費繳到哪天。「人還在但還沒續繳」是兩個欄位組合出來的狀態。
path_code and path_level are filled togetherpath_code 和 path_level 一起有值或一起為空 A level without a path, or a path without a level, makes no sense, so a CHECK requires both to be NULL or both to have a value. CHECK (path_level BETWEEN 1 AND 5) alone cannot do this: for NULL it gives UNKNOWN, and a CHECK only rejects FALSE.「沒有路徑卻有級數」或「有路徑卻沒有級數」都不合理，所以用一條 CHECK 規定兩者必須同時為 NULL 或同時有值。只靠 CHECK (path_level BETWEEN 1 AND 5) 做不到：遇到 NULL 時結果是 UNKNOWN，而 CHECK 只會擋下 FALSE。
Time limits stored on each speech每場演講都存時間規定 Different projects have different limits, so min_sec/max_sec are needed to judge each speech.不同專案的時間規定不同，所以需要 min_sec／max_sec 才能判斷每場演講有沒有超時。
No phone, email or address columns不存電話、Email 或地址 None of the questions need them. Collecting only what is needed protects privacy.所有查詢都用不到這些資料。只收集必要的資料，可以保護個資。
Each fact is stored in one place每件事只存一次 “Area A1 belongs to Division A” is stored once in areas, not repeated in every club row; a meeting stores only its club_id, not the club’s area. If a fact were copied into many rows, updating only some copies would leave the data contradicting itself. One deliberate exception: members.first_join_date could be computed as MIN(memberships.start_date), but it is kept so the date survives if old memberships are deleted; the two must be kept in step.「A1 屬於 Division A」只存在 areas 一次，不在每個分會的資料列重複；例會只存 club_id，不重複存分會的區域。如果同一件事複製在很多列，修改時只改到部分，資料就會互相矛盾。刻意保留的例外：members.first_join_date 其實可以用 MIN(memberships.start_date) 算出來，另外存是為了在舊會籍紀錄被刪除後仍保留這個日期；代價是兩邊要保持一致。
clubs has two candidate keysclubs 有兩個候選鍵 Both club_id and club_name identify a club. club_id is chosen as the primary key because a single short integer never needs to change; club_name stays a unique key, declared UNIQUE, so names still cannot repeat.club_id 和 club_name 都能唯一找到一個分會。選 club_id 當主鍵，因為單一的短整數永遠不需要修改；club_name 保留為 unique key，宣告成 UNIQUE，名稱依然不能重複。
